# Deploying TakeYouUp for free

Three free services, none of which required a card at the time of writing.
**Verify that yourself before signing up** — free-tier terms change often, and
Render in particular has mixed user reports about card requirements.

| Piece | Service | What it runs |
|---|---|---|
| Database | Aiven for MySQL (free) | MySQL 8, 1 GB |
| API | Render (free web service) | the Docker image in `takeyouup-backend/` |
| Frontend | Netlify (free) | the built React app + a proxy to the API |

You do the signups; nothing here needs credentials on your machine.

---

## Why these three

**Aiven over TiDB for the database.** TiDB's free tier is larger (5 GB), but
this schema leans on foreign keys throughout — `user_progress`, `certificates`,
`quiz_attempts`, the whole resources tree — and TiDB's foreign-key support has
caveats that real MySQL doesn't. Aiven runs actual MySQL 8, so the Flyway
migrations and the Hibernate dialect work unchanged. Take TiDB only if you hit
the 1 GB ceiling, and test the migrations first.

**Netlify over Cloudflare Pages for the frontend.** Pages
[cannot proxy to an external origin](https://developers.cloudflare.com/pages/configuration/redirects/) —
its `_redirects` only rewrite within the same site. Netlify can, which is what
lets the browser talk to a single origin. That matters: it keeps the app's
host-relative `/api` and `/uploads` paths working exactly as they do behind
nginx locally, and means **no CORS configuration anywhere**.

## 1. Database (Aiven)

1. Sign up at aiven.io, create a **MySQL** service on the **Free** plan.
2. From the service overview, note *Host*, *Port*, *User*, *Password*, *Database*.
3. Build the JDBC URL — Aiven requires TLS:

```
jdbc:mysql://HOST:PORT/DATABASE?sslMode=REQUIRED&serverTimezone=UTC
```

Flyway creates the whole schema on first boot; there is nothing to import.

## 2. API (Render)

1. Push this repo to GitHub, then **New → Blueprint** on Render and point it at
   the repo. It reads [`render.yaml`](render.yaml).
2. Set these in the dashboard (they are deliberately `sync: false`, so they
   never live in the repo):

   | Variable | Value |
   |---|---|
   | `SPRING_DATASOURCE_URL` | the JDBC URL from step 1 |
   | `SPRING_DATASOURCE_USERNAME` / `_PASSWORD` | from Aiven |
   | `GEMINI_API_KEY` | your own key |
   | `APP_FRONTEND_URL` | your Netlify URL (step 3) |
   | `MAIL_*` | your SMTP provider, or leave unset |

   `JWT_SECRET` is generated by Render automatically — don't set it by hand.
3. Deploy, then check `https://YOUR-SERVICE.onrender.com/actuator/health`.

## 3. Frontend (Netlify)

1. **Add new site → Import from Git**, pick this repo. Netlify reads
   [`netlify.toml`](netlify.toml), so the build settings are already correct.
2. **Edit `netlify.toml` first**: replace both occurrences of
   `https://takeyouup-api.onrender.com` with your actual Render URL.
3. Deploy. Then set `APP_FRONTEND_URL` on Render to the Netlify URL, so
   verification and password-reset emails link back to the right place.

## Fitting Render's 512 MB

This is the part that actually decides whether the free tier works. With
default JVM settings the API idles at **~500 MB** and would be killed. The
settings in `render.yaml` bring that to **~285 MB idle, ~300 MB under load**,
measured in a container capped at 512 MB:

| Setting | Why |
|---|---|
| `MaxRAMPercentage=55` | metaspace, thread stacks and the code cache live *outside* the heap — a "384 MB heap" container overshoots 512 MB |
| `UseSerialGC` | G1 reserves region metadata that is pure overhead at this size |
| `TieredStopAtLevel=1` | less JIT memory, and a faster cold start |
| `MaxMetaspaceSize=128m`, `ReservedCodeCacheSize=64m` | hard ceilings on the two biggest non-heap consumers |
| `Xss512k` | 20 Tomcat threads × 1 MB default stacks adds up |
| `DB_POOL_MAX=5`, `SERVER_TOMCAT_MAX_THREADS=20` | 20 connections and 200 threads are sized for a real server |

## Known limits of this setup

- **Cold starts.** Free services sleep after 15 minutes idle. The first request
  then waits ~30–60 s for the JVM. Fine for a portfolio link; poor for real
  users. Any paid tier removes it.
- **Uploaded images do not survive a deploy.** Course covers are written to the
  container filesystem, which Render's free plan does not persist. Seeded SVG
  covers regenerate; anything uploaded through the admin panel is lost on
  redeploy. Fixing it properly means object storage (Cloudflare R2, Supabase
  Storage, Backblaze B2 all have free tiers).
- **Email.** Mailpit is a local dev container and will not exist in production.
  Leave `MAIL_*` unset and the app degrades gracefully — sends fail, are logged
  with the link, and nothing breaks — but users cannot verify addresses or reset
  passwords. Point it at a real SMTP provider before inviting anyone.
- **1 GB of MySQL.** Plenty for the seeded catalogue and a few hundred users.

## Before you go public

`APP_ENV=production` (set in `render.yaml`) arms a startup check that **refuses
to boot** if the app is still using the development secrets committed to this
repo — the JWT signing key in particular, which anyone reading the source could
otherwise use to forge an admin token. If the deploy fails with
*"Refusing to start with development defaults"*, read the message: it names
exactly which variable is wrong.

Two things to do regardless of hosting:

- **Revoke the Gemini API key committed in `docker-compose.yml`** and issue a
  new one. It is in the git history and should be treated as public.
- **Rotate any GitHub token** that has been shared or pasted anywhere.
